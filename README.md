# ModelPro

Бэкенд Telegram-бота, который вычитывает кастинговые каналы, извлекает из
постов структурированные вакансии через LLM и рассылает их только тем
пользователям, кому они подходят по анкете. Живёт как
[@ModelProAgency_bot](https://t.me/ModelProAgency_bot) с Mini App на
modelpro.agency.

Кастинги публикуются россыпью Telegram-каналов, без единого формата и без
фильтрации по городу, полу, возрасту, ставке. Один и тот же пост форвардится
в десяток каналов за час. Вручную мониторить это нереально: большая часть
потока не подходит конкретному человеку, а редкие совпадения тонут в шуме.
Готовых агрегаторов под русскоязычный кастинг-рынок с матчингом по типажу я
не нашёл, поэтому собрал свой: userbot читает каналы напрямую через Telethon
(не через Bot API, это даёт доступ к приватным чатам), LLM превращает текст
в структуру, дальше идёт обычный матчинг по анкете и рассылка.

## Стек и требования

Backend: Python 3.11, FastAPI 0.115.5, aiogram 3.13.1, Telethon 1.36.0,
SQLAlchemy 2.0.36 (async) + asyncpg 0.30.0, Alembic 1.13.3, PostgreSQL 16.
Точные версии в `requirements.txt`, dev-зависимости (pytest 8.3.3,
pytest-asyncio 0.24.0) в `requirements-dev.txt`.

Frontend (Mini App): React 18.3, TypeScript 5.6, Vite 5.4, Tailwind CSS 3.4.
Версии в `webapp/package.json` заданы диапазонами (`^`), не зафиксированы
намертво.

Для запуска нужен Docker + Docker Compose. Для локальной разработки без
контейнера нужны Python 3.11 и локальный PostgreSQL 16.

## Установка и запуск

```bash
git clone git@github.com:sankficeba/model_pro.git
cd model_pro
cp .env.example .env
```

Заполни в `.env` как минимум `TG_API_ID`, `TG_API_HASH` (my.telegram.org →
API development tools), `TG_PHONE`, `BOT_TOKEN` (от @BotFather) и
`TG_CHANNELS`. Дальше:

```bash
docker compose up --build
```

При первом запуске Telethon запросит код подтверждения. Он не появится в
обычном `docker compose logs`, а ждёт ввода в интерактивном stdin
контейнера:

```bash
docker compose logs -f app     # смотришь, что контейнер ждёт код
docker attach tg_parser_app    # сюда вводишь код из Telegram
```

После авторизации файл сессии осядет в `./sessions/` (volume). Не удаляй
эту папку, иначе авторизацию придётся проходить заново.

При локальном запуске без Docker миграции нужно накатить руками:
`entrypoint.sh` делает это автоматически только внутри контейнера.

```bash
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
alembic upgrade head
python main.py
```

Mini App разрабатывается отдельно от бэкенда:

```bash
cd webapp
npm install
npm run dev
```

## Конфигурация

Не все переменные из `.env.example` одинаково критичны. Вот те, ошибка в
которых даёт заметный эффект:

| Переменная | Тип / default | Что будет, если не задать или ошибиться |
|---|---|---|
| `TG_API_ID`, `TG_API_HASH`, `TG_PHONE` | обязательны | pydantic-settings падает при старте с `ValidationError`, приложение не поднимется вообще |
| `BOT_TOKEN` | обязателен | aiogram `Bot` не создастся, старт падает так же |
| `TG_CHANNELS` | строка, `""` | приложение стартует, но userbot никого не слушает |
| `LLM_PROVIDER` | `stub` \| `openai` \| `ollama`, default `openai` | при `openai` без `OPENAI_API_KEY` фабрика (`llm/factory.py`) кидает `RuntimeError` на старте |
| `OPENAI_BASE_URL` | default `https://api.openai.com/v1` | смена одного этого поля переключает на любой OpenAI-совместимый провайдер, проверено на DeepSeek, без единой правки кода |
| `LLM_RETRY_MAX_AGE_HOURS` | int, default `48` | сообщения из retry-очереди старше этого возраста тихо отбрасываются без уведомления пользователю |
| `DATABASE_URL` или пять `POSTGRES_*` | опционально | если не задать ничего, соберётся дефолтный DSN `tg_parser:tg_parser@postgres:5432/tg_parser`. В проде это обязательно переопределить, иначе пароль от боевой БД останется дефолтным из репозитория |
| `ADMIN_IDS` | строка Telegram user_id через запятую, `""` | без этого никто не получает алерты про исчерпанный баланс LLM, а `is_admin_user()` всегда возвращает `False`, поэтому админ-панель в Mini App не откроется никому |
| `YOOKASSA_SHOP_ID` / `YOOKASSA_SECRET_KEY` | строки, `""` | без них `yookassa_client.is_configured()` вернёт `False`, эндпоинт `/api/subscription/checkout` ответит 503, остальной функционал продолжит работать как обычно |
| `YOOKASSA_WEBHOOK_TOKEN` | строка, `""` | если не задать, вебхук ЮKassa принимает запросы вообще без проверки shared-secret (остаётся только сверка `payment_id` с БД) |

## Как это устроено

```
Telegram-каналы → Userbot (Telethon)
                       │
                       ▼
              нормализация текста + SHA-1 (db/dedup.py)
                       │
              уникальный текст? ──нет──▶ привязать к канонической копии
                       │ да
                       ▼
              LLM.extract() → PostExtraction (Pydantic)
                       │
                       ▼
              db/matching.py: диспетчер по категории вакансии
              (creative / event / general / admin: своя таблица профилей
               и свой набор правил на каждую)
                       │
                       ▼
              aiogram Bot → уведомление тем user_id, кто прошёл матчинг
```

LLM-провайдер реализован как абстрактный класс `LLMProvider` (`llm/base.py`)
с системным промптом на ~800 строк, который просит модель вернуть JSON с
категорией, городом, ставкой и списком вакансий внутри одного поста (один
пост может содержать сразу несколько ролей разных категорий: например,
«нужны актёры + хостес на мероприятие» встречается регулярно). Ответ
валидируется Pydantic-схемой (`PostExtraction`/`VacancyExtraction`); если
JSON не распарсился, ставится `confidence=0.0`, пост просто не считается
кастингом, пайплайн не падает.

Один и тот же пост часто репостится в десятки каналов. Гонять каждую копию
через платный LLM-вызов бессмысленно, поэтому `db/dedup.py` вычищает из
текста `Forwarded from ...`, ссылки на t.me, `@упоминания` и эмодзи,
схлопывает пробелы и берёт SHA-1 от результата. LLM вызывается один раз на
уникальный текст, дубликаты привязываются к канонической записи без единого
лишнего запроса.

Отдельно от бота крутится FastAPI (`api/`), REST для Mini App. Авторизация
там не через токены, а по официальной схеме Telegram: фронт шлёт
`X-Telegram-Init-Data`, бэкенд проверяет HMAC-SHA256 подписи секретом,
производным от `BOT_TOKEN` (`api/auth.py`).

## Что видно в логах, если всё работает

Успешное извлечение из `_handle_message`:

```
LLM extract: casting=True project=['kino_serial'] city=Москва vacancies=1 conf=0.90
```

Ретрай-луп раз в 5 минут, когда очередь непустая:

```
LLM retry: отброшено 2 устаревших сообщений (старше 48ч)
LLM retry: 50 сообщений в очереди
```

## Известные ограничения и подводные камни

Userbot работает как один процесс с одной Telethon-сессией. Горизонтально
это не масштабируется: LLM-вызов сейчас синхронный внутри обработчика
сообщения, и при росте числа каналов поток обработки будет упираться в
него. Вынести экстракцию в отдельную очередь (Celery/RQ) было бы понятным
следующим шагом, но пока не сделано.

Дедуп репостов построен на эвристике regex-нормализации, а не на чём-то
более строгом. Она откалибрована под форматы шапок в тех каналах, которые
сейчас мониторятся. Канал с нестандартным оформлением форварда может
проскочить мимо дедупа как новый пост.

Провайдеры LLM не унифицированы по коду billing-ошибки. OpenAI отдаёт `429`
на исчерпанный баланс, DeepSeek отвечает `402`. Оба сейчас ловятся явно в
`llm/openai_provider.py` и уходят в retry-очередь вместо тихой потери
сообщения. Поймал это не с первого раза: при переключении на DeepSeek 402
изначально падал в общий `except Exception`, сообщение помечалось
`confidence=0.0` и терялось без ретрая и без алерта. Заметил это уже в
проде по логам, не по тестам. Если завтра добавится третий
OpenAI-совместимый провайдер с ещё одним кодом ошибки, та же дыра
вернётся, пока его явно не добавить.

Из той же категории: retry-очередь изначально обрабатывала сообщения в
порядке получения, без ограничения по возрасту. При простое LLM-провайдера
на несколько дней очередь выросла до 15 057 сообщений, и после
восстановления баланса пользователям посыпались уведомления о кастингах
недельной давности, которые давно закрылись. `LLM_RETRY_MAX_AGE_HOURS`
появился именно после этого случая, задним числом, а не заранее.

Тесты (`tests/`, 15 модулей, pytest + pytest-asyncio) покрывают матчинг по
всем категориям, дедуп, нормализацию ответов LLM и Pydantic-схемы.
Работают детерминированно, на `stub`-провайдере, без сетевых вызовов. В CI
их нет: `.github/workflows/deploy.yml` только собирает образ и катит на
прод при пуше в `main`, тестов как гейта перед деплоем сейчас не стоит.
Если матчинг сломан, узнаешь об этом, руками прогнав `pytest` перед
пушем, либо от пользователей после деплоя.

Frontend тестами не покрыт вообще.

CORS в `api/main.py` стоит `allow_origins=["*"]`. Осознанный компромисс:
в проде перед API всё равно один origin через reverse-proxy, но если API
станет доступен напрямую, это стоит сузить.

Приватные каналы userbot пытается заджойнить сам через
`JoinChannelRequest`, но это работает только если у него уже есть доступ:
без инвайт-ссылки на аккаунт, под которым поднята Telethon-сессия,
вступить руками всё равно придётся. Поле `channels.joined_at` остаётся
`NULL`, пока это не произойдёт, и ретрай-попытка джойна повторяется при
каждом старте.

## Troubleshooting

**Логи показывают `LLM retry: баланс ещё не пополнен, прерываем`, живые
уведомления не приходят.** У LLM-провайдера кончился баланс. Сообщения не
теряются, а копятся с `llm_retry_needed=true`, раз в час админам из
`ADMIN_IDS` прилетает алерт в Telegram. Пополнить баланс, дальше очередь
дожуётся сама батчами по 50 раз в 5 минут; всё, что старше
`LLM_RETRY_MAX_AGE_HOURS`, будет тихо отброшено без уведомления.

**Приватный канал добавлен через `/addchannel`, но посты не парсятся.**
Userbot не смог вступить сам. Нужно вступить вручную по инвайт-ссылке под
тем Telegram-аккаунтом, на который заведена Telethon-сессия.

**`docker compose up` на первом запуске выглядит зависшим.** Это не
зависание: Telethon ждёт код подтверждения на интерактивном stdin.
`docker compose logs -f app` покажет ожидание, код вводится через
`docker attach tg_parser_app`, а не в обычный лог.

**`alembic upgrade head` падает с конфликтом ревизий.** Кто-то накатил
контейнер на старом образе поверх уже более новой БД (или наоборот,
откатили образ без отката миграции). Смотреть `down_revision` в
`migrations/versions/` на актуальную цепочку, руками `alembic_version` в
БД не трогать без понимания, что делаешь.

**После смены `.env` на сервере поведение не меняется.** `docker compose
up -d` без `--force-recreate` не пересоздаёт контейнер, если сама
compose-конфигурация не поменялась: переменные окружения читаются
`pydantic-settings` один раз при старте процесса. Нужен
`docker compose up -d --force-recreate app` (или соответствующий сервис).
